# AnyServe on Cloudflare Workers Free: native Durable Object control plane (no containers), v4

Status: proposal v4. v2 answered the v1 review; v3 closed the v2 findings; v4 closes the v3 findings, listed in section 3.2. This document contains no credentials.

## 1. Goal and non-goals

Run the AnyServe v2 execution control plane on **Workers Free + R2 Free**, without Cloudflare Containers. One `wrangler deploy` must work on a free account. Existing Rust and Python SDKs must work unchanged over `wss://` (wire protocol = `docs/cloudflare-plan.md` Contract B as implemented by `crates/anyserve-core/src/http_ws_service.rs` and `crates/anyserve-client/src/ws_transport.rs`).

Guarantees (same as the Rust runtime): each job has exactly one winning terminal commit; retries may execute an external handler more than once; a job that has exposed non-progress output to an `Invoke` caller is not silently re-run (`output_interrupted`).

Non-goals: horizontal scale (single DO), behavioural changes visible to SDKs, a $0 promise outside the published operating envelope (section 9).

### 2.1 Visible differences of the Free native mode (documented in `docs/deployment.md`)
- Terminal jobs are kept 24 h (container default: 7 days).
- `Heartbeat.Load.custom` is bounded to 64 entries / 8 KiB, held in memory only, and is empty right after a hibernation wake until the next heartbeat.
- Heartbeat 30 s / timeout 90 s (Rust default 5 s / 15 s) and console polling 10 s (`recommended_poll_ms`).
- A message larger than 32 MiB encoded is closed by the platform with 1009; below that the application rejects over-limit requests itself.
- The `$0` operating envelope of section 9 is a stated reference shape; beyond it the service sheds load.

## 4. State machine and durability

The native DO has its own private SQLite database and is the only writer, so it does **not** use the container journal's `scheduler_lease` TTL, `acquire()` or `renew()` (that protocol exists to arbitrate between processes). `src/storage.ts` stays untouched for container mode.

### 4.1 Generation, wake-up and reset (fixes #1)
- `native_runtime_meta` holds `generation` (initialised to 1, stored as text, handled as BigInt).
- An ordinary hibernation wake-up **keeps the generation**. `rehydrateAfterWake()` rebuilds in-memory structures from SQL and WebSocket attachments; jobs whose lease row has `cancelling = 0` stay assigned/running: they are not re-queued, `attempt_count` is not touched, a `max_attempts = 1` job whose worker is still connected is not failed. Leases with `cancelling = 1` are not running work but keep their worker reservation until resolved (4.6).
- Only an explicit administrative reset (documented command) increments `generation`, fences all leases and applies the Rust crash-recovery rules (re-queue, `attempts_exhausted` when attempts are used up).
- Event sequences are `(generation << 32n) + localSeq` computed with BigInt and stored without loss (two integer columns). After a wake in the same generation, allocation continues from the persisted high-water mark.

### 4.2 Connection identity and tenancy (fixes #2, auth items)
- Each control `Session` socket gets a monotonically increasing `conn_id`, persisted in `native_sessions.current_conn_id` and copied into the socket attachment. Messages, `webSocketClose` and grace timers act only if `attachment.connId == current_conn_id`; a late close of a replaced connection is ignored.
- Each lease has `native_active_leases.attempt_conn_id`, set only when `AttemptOpen` is accepted. Resuming a control session keeps live data sockets; only a new `AttemptOpen` for that lease replaces the uploader.
- Pre-upgrade auth (`verifyWorkerHeaders` / `verifyClientHeaders`, errors returned as HTTP 401/16, 403/7, 400/3, 429/8 with `x-anyserve-grpc-code`) stores the authenticated `namespace` and `forced_pool` in the attachment. `AttemptOpen` for a live lease requires the active lease row, the current generation and `lease.namespace == attachment.namespace`. The `terminal_replay` branch is different: it needs only a stored winner/receipt with `(lease_id, namespace)` matching the attachment, **not** the current generation or an active lease row (4.5). Lease ids are unguessable (UUID).
- `Hello` validates `(worker_id, namespace, resume_session_id)` and `held_lease_ids`, sends `Welcome` first with `resumed_lease_ids`, then `Fence` for each held lease that is no longer valid.
- After every `await` (R2 read or write) the code re-checks, inside `transactionSync`, `(generation, conn id / attempt conn id, scoped job id, lease id, phase, cancelling)` before committing.
- Empty token sets mean anonymous mode exactly as in Rust; the default public endpoint therefore documents that `ANYSERVE_CLIENT_TOKENS` / `ANYSERVE_WORKER_TOKENS` must be set before exposing it.

### 4.3 Surviving hibernation (fixes #3)
- Attachments hold only **fixed-size** fields (<= 256 bytes): kind, id, connId, namespace, `lastSeenAtMs`, and scalar load (`queued`, `running`, `utilization`). `Heartbeat.Load.custom` is **never** put in an attachment (it can exceed the 16 KiB platform limit); it is kept in memory only, bounded to 64 entries / 8 KiB (excess is dropped and counted), and that bounded map is what `/api/workers` returns.
- `native_sessions` stores everything needed to schedule without a new `Hello`/`Credit`: interfaces, attributes, forced pool, total capacity, reserved capacity, max concurrency, last reported free slots, dispatched-since-credit, draining, connected, grace deadline. It is written on `Hello`, `Credit`, `Draining`, assign/release and disconnect, never on heartbeat. `grace_deadline_ms` is set **only** on the `connected 1 -> 0` transition, so repeated wake-ups never extend an already-disconnected session's grace.
- `native_jobs` covers durable jobs, `Submit` with explicit `EPHEMERAL`, and `Invoke`: spec, scoped id, queued-since, spillover, retry-at, absolute queue/execution/total deadlines, fairness/concurrency/affinity keys, caller conn id (NULL for `Submit`), streaming-input flag and `InputEnd` state, `winning_lease_id` and `result_digest`.
- **Row budget rule: objects are stored as packed bundles, not one row per object.** All static inline inputs, params and URI references of a job, when their encoded size (`manifest` + `pack_blob`) is <= 512 KiB, are written as **one** row in `native_object_bundles(scoped_job_id, role, seq, manifest, pack_blob)` with `role = 'static_in'` (a job with 24 one-byte objects, or up to the 1,024-object limit, writes one row). Completed outputs are likewise one `role = 'output'` row. **Overflow rules** (e.g. 48 inputs of 256 KiB = 12 MiB, each below the spill threshold): objects are packed in their original order, empty inline objects, URI objects and the params boundary included; whenever the next entry would push `manifest + pack_blob` past 512 KiB the current pack is closed and a new `seq` row begins, and a closed pack larger than 512 KiB is stored as an immutable R2 pack (<= 4 MiB, referenced from the manifest as `{ r2_key, offset, len }`). A single object > 512 KiB gets its own R2 blob. If a manifest alone exceeds 256 KiB it is split across ordered `seq` rows. Order, empty values, parameter boundaries and 4,096-byte previews (SUBSTR for inline packs, R2 Range at `offset` for R2 packs) are preserved. No multi-MiB value is stored in a single SQLite row. Streaming input chunks are persisted as they arrive (see 4.4) into the same kind of bounded rows.
- Watchers: `native_watchers(watch_conn_id PK, scoped_job_id, namespace, after_seq, delivered_seq, finished)` (64-bit sequences stored without loss). Each subscription restores its own next event, so two sockets watching the same job from different cursors resume independently. The cursor rule matches Rust exactly: `after == 0` or `after >= oldest - 1` is valid; an older non-zero cursor returns `OutOfRange(11)` with `oldest`.
- On wake, `getWebSockets()` (with `readyState`) is reconciled with SQL: sessions whose socket vanished start `reconnect_grace` (only if not already disconnected); non-terminal `Invoke` jobs whose caller socket vanished are cancelled once; vanished `Watch` subscriptions are dropped. Concurrent connections are capped (256 sessions, 256 attempt sockets, 128 invokes, 256 watches, and a small handshake-pending cap) so the reconcile step stays within the SDK's 5 s connect timeout; `constructor_runs` and `boot_id` are exposed in `/metrics` and `/api/overview`.

### 4.4 Promised progress (fixes #4)
- Before sending an `Ack` or an `ExecutionEvent`, the DO persists `last_frame_seq`, `exposed` (set when a non-progress `Output` enters the job log), the event high-water mark, the oldest readable cursor and events not yet delivered to the primary `Invoke` caller (table `native_job_events`, bounded).
- **Nothing the DO has received is held only on the heap when a handler returns, because the DO may hibernate between any two messages while the connection stays open.** Result upload (`ResultChunk`, 64 KiB) rules:
  - A single-chunk object (`last` on its first chunk, the reference-job case) needs no tail staging; it goes straight into the output bundle in the transaction that precedes the `Ack`/commit.
  - For a multi-chunk object **every arriving chunk is written to `native_upload_tail(lease_id, attempt_conn_id, obj_index, chunk_seq, data)` before `webSocketMessage` returns** (SDK chunks are <= 64 KiB). So chunk 33 is durable even if no `Ack` has been sent for it and the DO hibernates immediately; chunk 34 then continues byte-exact.
  - When the tail reaches `UPLOAD_SEGMENT_BYTES = 2 MiB` (half of the 4 MiB attempt window), when `last` arrives, or when the unacknowledged window slack drops below 1 MiB, the tail is **sealed**: written as an immutable R2 object (`native/v1/<do_id>/blobs/<uuid>`, via the 4.5 staging protocol) or, for a short final piece, an inline BLOB, and recorded in `native_upload_segments(lease_id, attempt_conn_id, obj_index, seg_index, byte_len, r2_key | blob)`. In the same transaction the sealed tail rows are deleted, and the contiguous `Frame`/result high-water and assembler state (current index, metadata, running `total`) are updated. Only after that transaction is `Ack` sent. An 8 MiB result is at most 4 segments; the sender is never stalled (a full 4 MiB window = two segments, and a tail ACK is sent as soon as slack requires it).
  - The cost is explicit: a large multi-chunk object costs about one row write per 64 KiB chunk plus one delete per chunk (or one growing tail row updated per chunk) in addition to the segment rows, which is why jobs with objects larger than one chunk are outside the reference job of section 9 and have their own, lower daily cap.
  - Streaming `InputChunk`s of an `Invoke` are likewise persisted before the handler returns (<= 512 KiB inline in the bounded stream-input rows, larger first spilled to R2), so no received input exists only on the heap. `InputEnd` is persisted too.
  - Server-to-worker `InputData` is sent in synchronous batches (<= 1 MiB / 16 chunks while `bufferedAmount` allows). The send position `(input object index, byte offset, last sent seq)` is written to the lease row **in the same synchronous turn** as the `ws.send()` calls (no `await` in between), so a hibernation can never fall between "queued" and "recorded" and the SDK never sees a duplicated or missing slice on the same socket.
- Before sending an `Ack` or an `ExecutionEvent`, the DO also persists `last_frame_seq`, `exposed` (set when a non-progress `Output` enters the job log), the event high-water mark, the oldest readable cursor and events not yet delivered to the primary `Invoke` caller (table `native_job_events`, bounded).
- A **new** `AttemptOpen` (new `attempt_conn_id`) discards that lease's uncommitted tail and segments (queued for R2 GC) because the SDK resends results from object 0 (`ResultChunk` has no offset).
- Retry rules match Rust: progress-only output allows retry; after exposed output a retryable failure ends an `Invoke` with `output_interrupted`.
- `Watch(after_sequence = 0)` starts at the oldest readable event; the cursor `after == oldest - 1` is valid (it returns events from `oldest`), only an older non-zero cursor returns `OutOfRange(11)` carrying `oldest`; archived terminal jobs get synthesised `Accepted` + `Finished` exactly like `runtime/mod.rs`. A live caller never receives a spurious `CursorExpired` caused by a wake.

### 4.5 Idempotent commit (fixes #5)
- Accept is committed before `SubmitResponse` / `Accepted` is sent. Attempt count and lease reservation are committed before `Assign`. Terminal state, result references, receipt and lease release are committed in **one** `transactionSync` before `AttemptFinished::COMMITTED` is sent.
- **Receipts.** The winning `(lease_id, result_digest)` of a job is stored on `native_jobs` and lives exactly as long as the job (for durable jobs: the whole archive retention), so a valid worker can still `Open` the lease and get `terminal_replay` while the job is archived. `native_receipts(lease_id PK, scoped_job_id, namespace, outcome_digest, created_at_ms)` additionally covers ephemeral completions and superseded retry attempts for `receipt_retention_ms` (10 min, > the SDK's 6 min automatic retry window). Replay is looked up by `(lease_id, namespace)` in both places and does **not** require the current generation or an active lease row, so it works across an administrative reset. Same digest returns `COMMITTED`, a different digest `REJECTED`; an expired `Open` with no receipt gets `AttemptFinished::FENCED` in a normal envelope.
- **R2 keys and GC with mutual exclusion.** Keys are immutable `native/v1/<do_id>/blobs/<uuid>` (the prefix contains this deployment's DO id, so several native deployments can share a bucket without ever reclaiming each other's objects), never `jobs/<job>/<role>/<idx>`. `native_r2_gc(upload_id PK, r2_key, state, expires_at_ms, retry_after_ms)`. Before `await r2.put`, the writer inserts `state = 'staging'`. To publish, the commit transaction runs `DELETE FROM native_r2_gc WHERE upload_id = ? AND state = 'staging' RETURNING upload_id`; if no row is returned the sweeper has already claimed the upload (`state = 'deleting'`), so the writer does **not** publish the reference and issues a compensating `r2.delete`. The sweeper moves an expired `staging` row to `deleting` with a conditional update before deleting and retries failed deletes. A periodic, paged reconciliation of the `native/v1/<do_id>/blobs/` prefix (each page is a Class A operation and is metered) deletes only keys that are unreachable from `native_object_bundles`, `native_upload_segments`, the stream-input rows and `native_r2_gc`, and older than a safety age, which removes late-arriving PUTs and anything interrupted mid-handler. Purge and eviction insert `pending_delete` rows **in the same transaction** that drops the reference; deletion removes the row only on success. Reusing a job id can never delete another job's object, and every committed reference stays readable.

### 4.6 Cancel, retry and reset (fixes v2 #4)
- A client cancel or execution timeout sets `cancelling = 1` and `cancel_deadline_ms` on the lease and sends `Cancel`. The worker's slot/capacity reservation is **kept** until `CancelAck`, a late `Finish`, session loss, or `cancel_grace` expiry, even if the job itself is already terminal. After a wake only leases with `cancelling = 0` count as running work, while `cancelling = 1` leases keep their reservation until resolved.
- A retryable `Finish` writes, in one transaction: the old attempt's receipt, the lease release, `failed_workers`, the next `retry_at_ms`, the `AttemptRestarted` event. The wake-up for `retry_at_ms` is armed **before** `COMMITTED` is sent, and in addition `rehydrateAfterWake()` and every `alarm()` scan for jobs that are queued with an overdue `retry_at_ms` and dispatch them. So if the DO is interrupted between the commit and `setAlarm` and no new request ever arrives, dispatch still resumes at the next alarm or wake.
- `last_frame_seq` and `exposed` are per attempt (a new attempt restarts at sequence 1). `exposed` is set only for a primary `Invoke` that has emitted non-progress output; durable `Submit` with a `Watch` still retries per the Rust rules. An administrative reset fails exposed `Invoke` jobs with `output_interrupted` (or cancels them if the caller is gone).

## 5. Protocol, sizes and flow control

### 5.1 Size limits (fixes #6)
There is no universal 1 MiB frame. Limits are per message type and equal to container mode (`deploy/cloudflare/server.toml`): `max_inline_object_bytes = 8 MiB`, `max_inline_total_bytes = 24 MiB`. The platform ceilings are 32 MiB per received WebSocket message (the edge closes with 1009 and the application cannot send an error envelope) and 100 MB per HTTP body; 24 MiB of inline data plus protobuf/metadata overhead stays below 32 MiB. Entry points that receive one whole message (`InvokeStart`, `Invocation::send` chunk, HTTP `SubmitRequest`; and in the other direction `ExecutionFinished.outputs`, `GetJob(include_outputs=true)`) accept their full declared range after an encoded-length check. Worker `Frame`/`ResultChunk` and server-to-worker `InputData` stay chunked at `Welcome.limits.max_chunk_bytes` (64 KiB). `Welcome.limits` matches the Rust defaults (256 KiB control, 64 KiB chunk, 4 MiB attempt window, 64 KiB assign-inline). R2 spill (> 512 KiB) is invisible to callers: inline stays inline and caller-supplied URIs stay opaque. Limits are enforced on both logical bytes (8/24 MiB inputs and params; data in 64 KiB chunks) and **actual encoded length**: the 24 MiB budget covers inputs and params only, so scheduling hints, metadata, URIs and envelopes are counted separately. A received or sent WebSocket message is accepted up to exactly 32 MiB (33,554,432 bytes) encoded, the Rust single-frame limit and the platform ceiling; the platform closes anything larger with 1009, and the application checks the encoded length itself below that, so the boundary tests assert both outcomes. HTTP unary bodies are capped at the Rust limit of 64 MiB. A `3 x 7 MiB` result (one ~21 MiB `ExecutionFinished` message) is encoded into a **single** pre-sized JS buffer from object references (no second JS copy), but the locked `workerd` copies the bytes again inside `ws.send()` (`kj::heapArray`) and keeps that copy in its send queue until it drains, so a message of encoded length `L` needs about `2L` transiently and `L` for as long as it sits in the queue. The memory plan below budgets for that; the 8 MiB per-job event budget counts `Finished` by its reference overhead (as Rust does), while the real bytes are reserved against the large-send budget.

### 5.2 Back-pressure (fixes #7)
- `max_chunk_bytes > 0`, `attempt_window_bytes >= max_chunk_bytes`. `Ack.up_to_sequence` = contiguous `Frame.sequence` high-water (a duplicate re-acks the high-water mark, a gap is `InvalidArgument`). `Ack.result_bytes` = the assembler total including 64-byte per-object overhead, metadata and URI bytes. ACKs are sent early enough that the SDK's shared window never deadlocks, including on short tails and the last chunk; results are assembled from index 0, `last` closes an object, a half-finished object at `Finish` is an error.
- `ws.send()` only enqueues, and the runtime copies the payload, so outbound bytes are budgeted explicitly and the budget counts native memory, not only the JS heap. Isolate budget (128 MB isolate): **80 MiB in-flight cap** for payload-related memory (uploads, R2 read buffers, encode buffers, outbound queues), leaving the rest for V8, SQLite and code. Any outbound message of encoded length `L` reserves `2L` plus a <= 2 MiB R2 read buffer **before the JS buffer is allocated**; after `ws.send()` returns the JS part is released and `max(bufferedAmount, L)` stays reserved until the queue drains or the socket fails at `consumer_stall_timeout`. Large terminal sends (`L` > 1 MiB) additionally go through a dedicated **large-send budget of 56 MiB**: one 21 MiB `Finished` (`2L` = 42 MiB) is admitted, a second concurrent one waits (asynchronously, without blocking other traffic) until enough of the first has drained. Per-socket `bufferedAmount` and the per-job 8 MiB unconsumed primary-`Invoke` event cap still apply. A stalled primary `Invoke` reader delays worker ACKs and the job fails at `consumer_stall_timeout` (30 s); a slow `Watch` is dropped without stalling workers; `Ack`, cancel and `Finished` frames bypass the input-pump queue.

### 5.3 Ordering and framing (fixes #8)
- Unary: HTTPS POST, raw protobuf in and out; failures keep HTTP status, decimal `x-anyserve-grpc-code` and text body.
- WebSocket: every upstream binary message is one bare protobuf; downstream `00 || protobuf` or `01 || code || utf8` then close. First messages: `InvokeRequest.Start`, `WatchRequest`, `WorkerMessage.Hello`, `AttemptUp.Open`; missing `Hello`/`Open` expires per config with `DeadlineExceeded(4)` before closing.
- `Welcome` is the first control reply; `AttemptOpened` precedes any `InputData`. Input order: static objects (`object_index = Some(i)`, empty inline and URI objects included, metadata on the first piece, `object_end` on the last piece), non-empty params (`object_index = None`, `parameter_chunk`, `object_end`), streaming chunks, then a trailer (`object_index = None`, `last = true`). Inline `Assign` and `terminal_replay` do not wait for the trailer. `InputEnd` ends only the input direction.
- `ExecutionEvents` buffers `Finished` until EOF, so the DO sends the last business message and then `close(1000)`. Peer close handling: `1005` (no status from the peer) completes the handshake with a plain close; `1006` is an abnormal disconnect with no Close frame, so it runs the loss/cancel/reconnect logic and is never treated as success and never echoed. Reserved codes are never sent. The runtime answers protocol Pings automatically while hibernating; JS cannot send protocol Pings, so no fake text/protobuf pings are used. Idle `Watch`, `Invoke` and `Attempt` sockets are verified over public `wss://` (a control-socket heartbeat cannot keep the other TCP connections alive).

## 6. Workers Free budget

### 6.1 Heartbeat and grace defaults (fixes #9)
`heartbeat_interval_ms = 30000`, `heartbeat_timeout_ms = 90000`, `reconnect_grace_ms = 30000`, `cancel_grace_ms = 15000`, `receipt_retention_ms = 600000`. Heartbeat cost is about `N * 86400 / (20 * H)` DO requests/day (incoming WS messages count 20:1): 100 workers at 30 s = 14,400/day (at the Rust default of 5 s it would be 86,400). The Worker and DO each have their own 100k/day request quota, so budgets are tracked separately. Longer timeouts lengthen failure detection and the SDK's `4 x heartbeat_timeout` retry window; grace is configured separately from the timeout.

### 6.2 Console polling (fixes #10)
The console currently polls overview every 1 s and jobs every 0.8 s (about 194,400 requests/day for one visible tab). `ControlPlaneSummary` gains optional `recommended_poll_ms` (null = current behaviour for local/container servers). The native DO reports 10000 (env `ANYSERVE_CONSOLE_POLL_MS`; `0` = manual refresh button only). The console honours it for overview, jobs, detail and workers polling and keeps pausing when the tab is hidden.

### 6.3 Exact timers, zero-write heartbeat (fixes #11, v2 #3)
**Only `Heartbeat`** is attachment-only: it updates `lastSeenAtMs` in the socket attachment with no SQL write and no `setAlarm`. `Credit`, `Draining`, `AssignReply` and `CancelAck` commit their own state transitions (and also refresh `lastSeenAtMs`).

There is one alarm, set to `min(earliest exact business due time, next maintenance bucket)`. **Business timers are exact and never bucketed**: retry-at (Rust's first retry is 200 ms), spillover, queue/execution/total deadlines, `Hello`/`Open` handshake timeout, cancel grace, reconnect grace, consumer stall. A business transition that creates an earlier due time re-arms the alarm (an alarm that has fired or is missing is always re-armed). Only background maintenance is bucketed to >= 5 s: session-liveness sweep, receipt/GC sweep, purge. `alarm()` clears its in-memory marker first, reads the latest attachments, checks connection ids and absolute times, processes a bounded batch idempotently (late or duplicate runs are safe), then schedules the next due time. Deadlines are also checked lazily during dispatch and commit. No `setInterval`. Example: a job with a 2 s total timeout whose first attempt fails retryably is retried after 200 ms, not after a 5 s bucket.

### 6.4 Rows and storage (fixes #12, v2 B2, v3 3)
Results are persisted as sealed <= 2 MiB segments plus a per-chunk tail (4.4) and objects are packed into bundle rows (4.3). **Full-lifecycle row accounting for the reference job** (1 attempt, <= 24 small inputs in one bundle row, one small output in one bundle row, <= 4 events, 24 h retention), counting every UPDATE, DELETE and index write: job insert + its indexes (~3), input bundle (1), session reservation update (1), lease create (1) + `AttemptOpen` update (1), attempt-start update (1), terminal update + index (~2), output bundle (1), receipt (1), events (1-2), watcher cursor (0-1), lease delete (1), alarm arming (~2), next-day purge deletes of job, bundles, receipt, events and index entries (~8): **about 24-28 rows per job**. At 3,000 reference jobs/day that is 72,000-84,000 writes; admission control stops accepting at 90,000 and keeps the remaining 10,000 for accepted jobs' completion, cancel, alarms and purge. Row reuse still costs a write on every UPDATE, which is why the estimate is by lifecycle step, not by table. `native_quota_meter` is **not** updated per request or heartbeat: credits are reserved in memory in blocks (e.g. 500 row writes, 1,000 requests) and flushed inside transactions that are being written anyway, so a heartbeat (cold-wake included) causes zero SQL writes (25 workers would otherwise add ~72,000 writes/day). Alarms count as row writes. A rejected HTTP/Upgrade request has still consumed one ingress request, so shedding protects the remaining work but cannot guarantee that every arriving request gets an application-level answer.

## 7. Implementation structure (fixes #13)

- `native/proto.ts`: hand-written zero-eval codec (no protobufjs `new Function`) for `execution.proto`; BigInt for 64-bit values (> 2^53 survive memory and storage losslessly); `optional object_index` presence (`0` -> bytes `28 00`, `undefined` -> absent); unknown-field skipping; malformed lengths rejected; golden vectors from Rust prost.
- `native/identity.ts`, `native/auth.ts`: byte-exact `spec_hash` / `outcome_digest` / scoped ids, scheduling hints excluded, trace keys excluded, URI digest rules, UTF-8 byte ordering of map keys, constant-time token checks, role/namespace derivation, forced pool. The scoped-id bijection is exactly Rust's: a raw id in the `default` namespace is used bare **unless it starts with `@ns:`**, everything else is `@ns:<ns>:<id>`. So `("default", "@ns:team:j")` is stored as `@ns:default:@ns:team:j`, which differs from `("team", "j")` = `@ns:team:j`; both pairs are encode/decode, idempotency and import test cases.
- `native/engine.ts`: the state machine as a deterministic function of (state, input, clock) so it can be replayed against the Rust runtime (queue order, capacity, concurrency keys, affinity, pool spillover, retry/cancel, exposure rules). Old `spec_json` stays readable both ways.
- `native/store.ts`, `native-do.ts`, `native/console-api.ts`: storage, hibernation glue, `/api/*` parity (`/healthz` and `/readyz` keep their 204/503 semantics, `/metrics`, `/api/overview` with `memory_plus_cloudflare` and `public_endpoint` = env, else `wss://<host>`, `/api/jobs`, `/api/jobs/:id` with 4096-byte previews, cancel, `/api/analytics/jobs` retained + archive, `/api/workers`).

## 8. Storage path (fixes #14)
The native DO does not call `JournalStorage` (its `acquire()` materialises every queued job and input as base64, `commitBatch()` decodes whole objects before deciding to spill, reads call `arrayBuffer()` on whole objects). `native/store.ts` takes bytes and object references directly: the constructor (`blockConcurrencyWhile`, ~30 s platform timeout; SDK connect timeout 5 s) loads only bounded scheduling and session metadata, does no R2 I/O and reads no payloads; payloads stream on demand; previews use `SUBSTR` or R2 Range (4096 bytes). Canonical hashes for large objects are computed incrementally with `crypto.DigestStream` over length-prefixed canonical bytes (Web Crypto fallback in Node tests). The per-isolate memory budget counts runtime buffers, inputs, results, slow-subscriber queues, encode/hash copies and in-flight R2 data; the 32 MiB logical cache alone is not treated as proof of 128 MB safety. The Free-plan 10 ms CPU limit is the target for hot paths (the DO pages list a larger default; the effective limit on the target account is verified live).

## 9. Published $0 operating envelope (initial, to be confirmed by measurement)
The envelope is stated for a **reference job shape**, not just a count: 1 attempt, <= 24 small inline inputs totalling <= 16 KiB, <= 1 output object <= 16 KiB (<= 32 KiB inline in total, single-chunk objects only), <= 4 events, no R2, 24 h retention of terminal jobs, <= 1 watcher per job. Initial target: <= 25 workers online 24/7 at the Free defaults, **<= 3,000 reference jobs/day**, one foreground console tab at 10 s polling. Storage check: 3,000 x (~32 KiB payload + ~4 KiB rows/indexes) is about 108 MiB retained for 24 h, roughly a tenth of the 1 GB single-DO limit; admission also reserves the retained size of each accepted job and refuses new work when `databaseSize + reserved retained bytes` would exceed 850 MiB (this protects against jobs near the reference upper bounds, e.g. 256 KiB outputs, which would otherwise exceed 1 GB at 5,000/day). Jobs with objects larger than one 64 KiB chunk, or that use R2, have their own lower daily caps because of the per-chunk tail writes and R2 operations. The live run publishes a measured sample (rows, databaseSize, requests, R2 A/B) and the first rejected job.

Six quota dimensions are tracked (SQL `rowsRead`/`rowsWritten` from `sql.exec` exactly; ingress/DO requests, duration and R2 operations conservatively estimated and calibrated against the Cloudflare dashboards, with batched meter flushes per 6.4) and used for admission control on every path (Submit, Invoke, Watch, Get, retries, cleanup), with headroom reserved for accepted work:
1. Worker ingress requests and DO requests, 100,000/day each (WebSocket messages count 20:1; alarms and RPC count; 25 workers at 30 s heartbeats are ~3,600 DO requests/day; a console tab polling overview + jobs every 10 s is ~17,280 ingress and ~17,280 DO requests/day).
2. DO SQLite `rowsWritten`, 100,000/day (includes indexes, deletes, `setAlarm`).
3. DO SQLite `rowsRead`, 5,000,000/day.
4. DO duration, 13,000 GB-s/day, and DO storage (design <= 1 GB).
5. R2 Standard Class A, 1,000,000/month (PUT, LIST).
6. R2 Standard Class B, 10,000,000/month (GET, Range GET, HEAD), plus R2 storage <= 9 GB-month.
Daily DO quotas reset at 00:00 UTC; R2's free tier is monthly and overage is billed. The live run reports real values for a worked sample and the first request that is rejected.
